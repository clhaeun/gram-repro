## 1. 지시문 전제 대비 실제 코드 — 2건이 달랐다

| 지시문 전제 | 실측 | 조치 |
|---|---|---|
| "지금은 한 해만 골라 1행으로 저장" | **train 은 이미 전량 확장**(nq10 107,480행). `sidxs[:1]` 은 `convert_subset` 의 **test 분기에만** 있었다 | test 만 확장하면 됨 |
| "split 이 확장보다 뒤면 순서를 바꿔라" | split 은 `build_pairs:118-123` 에서 unique key 기준으로 **이미 먼저** 일어난다 | **변경 없음** |
| "행 하나 = group 하나로 맞춰라" | group = unique input 이었다 (nq10 train 36,907 group / 107,480행, 크기 평균 2.912 max 93) | **여기가 실질 변경** |

지시문의 결론("다해 입력의 실효 비중이 눌린다")은 맞지만 원인이 다르다. 행이 없어서가 아니라
`puzzle_dataset.py:25` 가 group 당 **정확히 1행만** 뽑기 때문이다:

```python
puzzle_id = rng.integers(group_indices[group_id], group_indices[group_id + 1])
```

group = unique input 이면 해 93개짜리 입력도 1 epoch 에 1행만 나와서 해 1개짜리 입력과
가중치가 같다. 사수님 로그 `Saved train: 107494 groups, 107494 puzzles` 는 group 수 == 행 수라
다해 입력이 k배 가중된다.

| 7 | 해 개수 분포 표 | §5 (사수님 dict 없어 단독 제시) |

**sidecar 는 byte 단위로 불변**이다 — 이동 전후 md5 동일:

`save_sidecar` 는 `build_pairs` 산출물만 쓰고 확장 로직을 타지 않으며 split seed 0 도 그대로다.
coverage 분모가 sidecar 라 이 불변성이 중요하다.

기존 acceptance 검사 `[5]`/`[6]` 은 옛 규율("group = unique input", "test 는 입력당 1행")을
하드코딩하고 있어 새 규율로 고쳐 썼다. 나머지 `[1]`~`[4]`, `[7]`~`[12]` 는 손대지 않았다.

## 4. ★ 학습 착수 전에 결정해야 할 것 2가지

### 4-1. epochs 재조정 (필수)

`pretrain.py:223`:
```python
total_steps = int(config.epochs * train_metadata.total_groups * train_metadata.mean_puzzle_examples / config.global_batch_size)
```
`total_groups` 가 늘었으므로 **같은 epochs 면 step 이 그만큼 늘어난다** (`global_batch_size=768`):

| | 기존 EPOCHS | step (uniq) | step (pair, 그대로 두면) | step 유지하려면 |
|---|---|---|---|---|
| 8×8 | 12000 | 68,375 | **112,406 (1.64배)** | EPOCHS≈**7299** → 68,371 |
| 10×10 | 1260 | 60,550 | **176,334 (2.91배)** | EPOCHS≈**433** → 60,597 |

- **step 유지**: uniq run 과 optimizer step 수가 같아 "확장만의 효과"를 분리할 수 있다. 다만
  다해 입력이 k배 가중되므로 데이터 1회 순회에 필요한 step 도 늘어, epoch 수로는 덜 본다.
- **epochs 유지**: step 이 1.64/2.91배가 되어 GPU 시간이 그만큼 는다(10×10 은 12시간 → 35시간).
  대신 uniq run 과 step 이 달라져 비교축이 하나 더 흔들린다.

**어느 쪽인지 지시 못 받았다. 임의로 정하지 않고 대기한다.**
`eval_interval` 도 같이 봐야 한다 — 8×8 은 `train_nqueens8_v2.sh:90` 에 `eval_interval=200`
**하드코딩**이라 EPOCHS 를 7299 로 낮추면 eval 이 60회 → 36회로 준다. 10×10 은 `EVALINT` 환경변수라 조정 가능.

### 4-2. harness / in-loop 축이 바뀐다

- **in-loop**: `nqueens/n_eval` 이 nq8 772→1,270, nq10 6,513→19,220 이 된다. 같은 입력이
  해 개수만큼 반복 평가되므로 **자동으로 pair 가중**이 된다. 기존 in-loop 수치와 직접 비교 불가.
- **harness**: `experiments/sweep_harness.py:214-216` 이 `all__inputs.npy` 를 **dedup 없이**
  그대로 읽는다(`B = len(inputs)`). 확장된 test 를 주면 중복 행마다 따로 20샘플을 뽑아
  `found(x)` 가 행별로 계산된다 — 같은 입력에 대해 20샘플을 **모아서** 세는 기존 정의와 다른 양이다.
  비용도 nq10 2.95배가 된다.
  → **기존 v5h/v6h 결과와 비교하려면 harness 는 `-uniq` 경로를 계속 써야 한다.**
  현재 `run_v5_harness.sh:64`, `run_v6_harness.sh:58` 의 기본 경로는 `data/nqueens-{n}` 이라
  **지금 그대로 돌리면 새 데이터를 읽는다.** 지시 주시면 `-uniq` 로 고정하겠다 (아직 안 고쳤다).
